# Транзакции для путей разрешения рядов — дизайн (тех-долг)

**Дата:** 2026-06-10
**Статус:** утверждён к реализации (одобрено Натали)
**Область:** боевой (`origin/main`) + демо (`demo-five-modes`) — общий код контроля рядов.

## 1. Зачем

Обработчики, которые разрешают конфликты/правят ряды, делают **несколько** записей в БД подряд (`INSERT`/`UPDATE`/`DELETE`) **без транзакции**. Если процесс упадёт или одна команда ошибётся **посередине** серии, остаётся «полузапись»: ряд снят у одного рабочего, но не записан другому (или наоборот), либо запись о спорном осталась/исчезла рассинхронно. Вероятность низкая (боевой — один пользователь, демо — лёгкая нагрузка), но дыра реальна и растёт при нескольких бригадирах. Чиним профилактически.

Изменение **невидимо для пользователя** — поведение то же; разница только при сбое: вся серия откатывается целиком (ряд либо переехал полностью, либо никак).

## 2. Что оборачиваем

Многозаписьные пути (общие для обоих контуров):

- **`POST /api/logs`** — ветка деления (`divide`): снять ряд со всех держателей + раздать долями нескольким рабочим.
- **`POST /api/logs/resolve`** — действия `divide` / `reassign` / `postpone` (несколько записей: правка/удаление исходной + новые записи + возможный занос в `disputed_rows`).
- **`POST /api/disputed/:id/resolve`** — `assign-actual` (деление ряда между N рабочими) / `return-first` (вернуть заявителю): несколько `INSERT` + `DELETE` из `disputed_rows`.

Однозаписьные обработчики (`POST /api/employees`, `DELETE /api/logs/:id` и т.п.) НЕ трогаем — одиночный запрос атомарен сам по себе.

## 3. Архитектура (Вариант A)

### 3.1 Новый helper `withTransaction(pool, fn)`

Единственная новая «умная» единица — под юнит-тесты, изолированно от HTTP/конкретных обработчиков. Размещение: `server/db.js` (новый маленький модуль) с `module.exports = { withTransaction }`.

```js
// Выполняет fn(client) внутри транзакции. COMMIT при успехе, ROLLBACK при ошибке.
// Клиент всегда освобождается. Результат fn пробрасывается наверх.
async function withTransaction(pool, fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    try { await client.query('ROLLBACK'); } catch { /* откат лучшее усилие */ }
    throw err;
  } finally {
    client.release();
  }
}
```

### 3.2 Рефактор общих хелперов — принимают `db`

`applyRowRemoval`, `insertDisputed`, `upsertWorkLog` сейчас обращаются к глобальному `pool`. Делаем первым аргументом **`db`** — «исполнитель запросов» с методом `.query(...)` (это либо клиент транзакции, либо сам `pool`). Внутри заменяем `pool.query(...)` → `db.query(...)`. Поведение идентичное; меняется только источник соединения.

Сигнатуры — добавляем `db` первым параметром к текущим (боевой и демо demo-aware, функции совпадают; точные сигнатуры из `origin/main` зафиксирует план):
- `applyRowRemoval(db, ownerCol, ownerVal, logId, rowNum, rowBushes)`
- `insertDisputed(db, d, owner, req)`
- `upsertWorkLog(db, ownerCol, ownerVal, req, ctx, emp, rowNum, bushes, weight)`

### 3.3 Обёртка обработчиков

В каждом из трёх путей: всё, что пишет (а также **гейтящие `SELECT`**, по которым принимается решение о записи — например «найти исходную запись», «найти спорный ряд»), уносим внутрь `withTransaction(pool, async (client) => { ... })`, передавая `client` в хелперы и в прямые `client.query(...)`. Валидация входных параметров и работа с инвентарём/парсером (чистое чтение, не БД) остаются снаружи транзакции. Финальный `res.json(...)` — после успешного коммита (вне колбэка).

Откат при ошибке: `withTransaction` пробрасывает ошибку → существующий `try/catch` обработчика отвечает 4xx/500 как сейчас. Никаких новых кодов ответа.

## 4. Крайние случаи

- **Гард 409 «ряд уже снят»** (есть в `reassign`/`postpone`): внутри транзакции проверка работает так же; при срабатывании — бросаем/возвращаем как сейчас, незаписанное откатывается.
- **Чтение инвентаря** (`getDemoInventory`/глобальный `parser`) — вне транзакции (не БД-запись; demo-инвентарь читается из своих таблиц до начала серии).
- **Вложенность:** `withTransaction` не вкладывается сам в себя — каждый путь оборачивается один раз на верхнем уровне; хелперы получают уже открытый `client`.
- **Ошибка ROLLBACK** (соединение уже мертво): глушим (best-effort), пробрасываем исходную ошибку — она важнее.

## 5. Тестирование

- **Юнит-тесты `withTransaction`** (`test/db.test.js`) с фейковым `pool`/`client` (метод `query` пишет вызовы в массив):
  - успех → последовательность `BEGIN`, …, `COMMIT`; `release()` вызван; результат `fn` возвращён.
  - `fn` бросает → `BEGIN`, …, `ROLLBACK`; ошибка проброшена; `release()` вызван; `COMMIT` НЕ вызван.
  - ошибка самого `ROLLBACK` не маскирует исходную ошибку; `release()` всё равно вызван.
- **Существующие тесты** (`node --test`, сейчас 52 в демо / соответствующий набор в боевом) — остаются зелёными (рефактор хелперов не меняет поведение; их вызовы в тестах, если есть, обновляются под новую сигнатуру).
- **Ручная проверка на демо:** обычные деление ряда / разбор спорного / переписать / отложить работают как прежде, кусты сходятся, дублей нет (видимых изменений быть не должно).

## 6. Что НЕ делаем (YAGNI)

- Не оборачиваем однозаписьные обработчики.
- Не добавляем повторные попытки (retry) при сериализационных конфликтах — уровень изоляции по умолчанию, одиночные короткие транзакции; ретраи избыточны для текущей нагрузки.
- Не меняем коды/тексты ответов и поведение для пользователя.
- Не трогаем миграции/схему БД.

## 7. Развёртывание

Оба контура, почти подряд (Вариант 2 — правка невидимая). Реализация — Subagent-Driven в git worktree от `origin/main` (канонический общий код). Затем:
- **Демо:** порт правок на `demo-five-modes` (cherry-pick/перенос), push в приватный SourceCraft, VPS `git pull` + `pm2 restart` (порт 3001), smoke + обычная операция деления.
- **Боевой:** PR в `origin/main` (Render автодеплой), smoke `/health`.

Клиент не меняется → **бамп кеша SW не требуется**. Боевой публичный репо — без секретов/бизнес-данных (как обычно).
