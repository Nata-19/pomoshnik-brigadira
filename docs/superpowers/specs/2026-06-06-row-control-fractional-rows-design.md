# Дробный учёт рядов при делении — дизайн

**Дата:** 2026-06-06
**Статус:** утверждён к реализации
**Область:** боевой + демо (общий код контроля рядов). Продолжение Фазы 2.

## 1. Проблема

Сейчас ряд — неделимая единица. При делении ряда между рабочими делятся **кусты**, но **номер ряда пишется каждому рабочему целиком**. Последствия:
- в подсчёте рядов поделённый ряд считается как целый у каждого → «всего за день» завышается (2 заданных ряда показываются как 3);
- у каждого рабочего ряд виден целым, нет долей (надо 0.5 / 1.5).

Натали (live, боевой): поделила 1 ряд между двумя, ждала 0.5 и 1.5 ряда, «всего за день» = 2; получила по 2 ряда и итог 3.

## 2. Решение (Подход А)

В каждой записи журнала хранить **вес каждого ряда**: целый ряд = 1, поделённый = доля (0.5, 0.33…). Отчёты и «всего за день» **суммируют веса**, а не считают номера. Дробь не вводится отдельно — она вытекает из кустов (или из равного деления в режиме «только ряды»).

Нужно и в `rows_bushes` (ряды+кусты), и в `rows_only` (только ряды) — в обоих на одном ряду бывает несколько человек.

## 3. Модель данных

Новая колонка `work_logs.row_weights` (**TEXT, JSON-объект** `{"<номер ряда>": <вес>}`).
- Обычная запись (ввод без конфликта): каждому ряду вес `1` → напр. ряды «1,2,3» → `{"1":1,"2":1,"3":1}`.
- Поделённый ряд: вес рабочего по этому ряду = его доля (`0.5`, `0.25`…).
- `rows` (CSV номеров) остаётся как есть — он по-прежнему источник «какие ряды», `row_weights` добавляет «с каким весом». Ключи `row_weights` всегда совпадают с номерами в `rows`.
- Для записей в режиме `hours` (рядов нет) `row_weights` = `NULL`/`{}`.

**Почему JSON по рядам, а не одно число:** при повторном делении одного ряда (например, потом добавили третьего рабочего) нужно знать вес именно этого ряда у каждого держателя, чтобы снять его и раздать заново без задвоения. Одним скаляром на запись это не выразить (в записи несколько рядов с разными весами).

## 4. Миграция (строго неразрушающая)

На старте сервера (рядом с прочими идемпотентными `ALTER` в init-БД):
```sql
ALTER TABLE work_logs ADD COLUMN IF NOT EXISTS row_weights TEXT;
```
Бэкфилл для существующих записей с рядами и пустым весом — проставить каждому ряду вес 1:
- Обходим записи, где `row_weights IS NULL AND rows IS NOT NULL AND rows <> ''`, и пишем `{"r1":1,...}` из их `rows`.
- **Ничего не удаляем и не меняем в существующих `rows`/`bushes`.** Боевые данные сохраняются (в боевом уже есть данные, которые менять нельзя — жёсткое требование).

Старые уже-поделённые ряды (если были) останутся с весом 1 у каждого держателя (прежнее задвоение в прошлом) — это осознанный компромисс Варианта 1 «считаем с этого момента».

## 5. Чистое ядро расчёта долей

Вынести в `server/rowControl.js` (рядом с `distributeBushes`) чистые функции, покрытые юнит-тестами:

- `rowWeightsByBushes(totalRowBushes, assignments)` — для `rows_bushes`. На входе всего кустов ряда и `[{employee, bushes}]`; на выходе `[{employee, weight}]`, где `weight = bushes / totalRowBushes` (точное число, без округления в хранении). Гард: `totalRowBushes <= 0` → веса по равному делению (как fallback).
- `rowWeightsEven(n)` → массив из `n` равных весов `1/n` (для `rows_only`, default). Сумма === 1 (последний добирает остаток, чтобы точная сумма была 1).
- `parseRowWeights(text)` / `serializeRowWeights(obj)` — JSON ↔ объект, безопасно к мусору (`{}` при ошибке).
- `sumRowWeights(records)` — сумма всех весов по массиву записей (для отчёта); возвращает точное число.
- `formatRows(weightSum)` — формат показа: округл. до 2 знаков, без лишних нулей (`2`, `0.5`, `0.33`).

Веса **храним точными** (например 1/3 как `0.3333333333`), **округляем только при показе** (Вариант Б: слагаемые до 2 знаков, итоги — от точной суммы).

## 6. Пути записи (где проставляется вес)

- **`POST /api/logs` (обычный ввод):** при формировании `row_weights` каждому ряду вес 1.
- **`applyRowRemoval(...)`:** при снятии ряда из записи — удалить ключ ряда из `row_weights` (и, как сейчас, из `rows`; пересчитать `bushes`). DELETE записи, если рядов не осталось.
- **`upsertWorkLog(..., rowNum, bushes, weight)`:** добавить/обновить ряд у рабочего — выставить `row_weights[rowNum] = weight` (при слиянии в существующую плашку — записать вес этого ряда; кусты и список рядов — как сейчас).
- **`divide` (действие resolve):**
  1. определить всего кустов ряда из инвентаря (как сейчас, `rowBushes`);
  2. **снять ряд со ВСЕХ текущих держателей** в разрезе (дата+хозяйство+квартал+клетка+вид работ): найти все записи, где ряд присутствует, и убрать его из каждой (через `applyRowRemoval`-логику по ряду) — это делает повторное деление корректным;
  3. посчитать веса: `rows_bushes` → `rowWeightsByBushes`; `rows_only` → `rowWeightsEven` или ручные доли;
  4. раздать отмеченным рабочим (`upsertWorkLog` с весом). Сумма весов ряда = 1.
- **`reassign` (другой день, переписать):** ряд переносится целиком — снять у прежнего (вес уходит), добавить новому с весом 1.
- **`postpone`:** ряд снят у рабочего (вес уходит), уезжает в «Спорные» (в журнале веса нет).
- **`/api/disputed/:id/resolve` (`assign-actual` / `return-first`):** те же правила долей; `return-first` → ряд целиком (вес 1) заявителю.

## 7. Подсказка про кусты в окне деления

Окно деления (`showDivideModal`) показывает **«в этом ряду N кустов»** (из инвентаря) — бригадир не помнит наизусть и не имеет бумажной инвентаризации.
- Число кустов ряда сервер уже знает (`getBushesCount`/инвентарь). Передать его клиенту вместе с информацией о конфликте (в ответе `POST /api/logs` при конфликте и/или в данных спорного ряда), чтобы модалка показала подсказку и могла подсказать остаток при ручном вводе кустов.
- В режиме `rows_only` подсказки про кусты нет (кустов нет) — показываем долю (по умолчанию поровну).

## 8. Отчёт и «всего за день»

В `GET /api/report`:
- Счётчик рядов берёт **сумму весов** (`sumRowWeights`) вместо `rowCountOf` (подсчёта номеров) — и в строках по рабочему/клетке, и в «Итого», и в «Всего за день».
- Показ — через `formatRows` (2 знака, без нулей). Итоговые суммы округляются от точной суммы весов.
- Кусты и часы — без изменений (целые, как сейчас).
- Демо-вкладка «Выполнение» (га), когда будем делать, тоже сможет опираться на веса (ряды→га станет честнее на поделённых рядах) — но это отдельная фича после Фазы 3; здесь только не сломать её основу.

## 9. Крайние случаи

- **`totalRowBushes = 0` или ряд без кустов в инвентаре** (`rows_bushes`): fallback на равное деление весов (`rowWeightsEven`), чтобы не делить на ноль.
- **Сумма весов одного ряда из-за округления показа** (1/3×3): внутри точно = 1; «всего за день» считается от точных весов → итог ровный.
- **Повторное деление:** ряд снимается со всех держателей перед раздачей (см. §6) → нет накопления >1.
- **Запись `hours`:** `row_weights` пустой/NULL, в подсчёт рядов не входит.
- **Старые записи без `row_weights`:** при чтении трактуем отсутствие как «каждый ряд = 1» (на случай, если бэкфилл не дошёл) — `sumRowWeights` при отсутствии веса берёт 1 за ряд из `rows`.

## 10. Тестирование

Юнит (`node --test`, `test/rowControl.test.js`):
- `rowWeightsByBushes`: 100 кустов, 25/75 → 0.25/0.75; сумма 1; пустой total → равное.
- `rowWeightsEven`: n=2 → [0.5,0.5]; n=3 → сумма ровно 1.
- `parse/serialize` round-trip; мусор → `{}`.
- `sumRowWeights`: запись без весов считается по числу рядов; смесь целых и долей суммируется точно.
- `formatRows`: 2→«2», 0.5→«0.5», 1/3→«0.33».

Интеграционно (ручная проверка Натали после деплоя):
- `rows_bushes`: 1 ряд на двоих (кусты пополам) → 0.5/0.5, «всего за день» совпадает с заданным; ряд + полный ряд у второго → 1.5; подсказка «N кустов» видна.
- `rows_only`: ряд на двоих → 0.5/0.5; ручная правка доли.
- Повторное деление того же ряда на троих → по 0.33, сумма 1.
- Разбор спорного и «переписать» — веса корректны.

## 11. Что НЕ делаем (YAGNI)

- Ввод доли ряда напрямую в `rows_bushes` (доля выводится из кустов).
- Исправление исторических уже-поделённых записей (Вариант 1: только вперёд).
- Изменение модели «одна плашка на рабочего» (остаётся).
- Транзакции на путях разрешения — прежний тех-долг, отдельным проходом (не здесь).
