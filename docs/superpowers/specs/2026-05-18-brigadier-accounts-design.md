# Дизайн Этапа 1: Бригадиры, вход и изоляция данных

**Дата:** 2026-05-18
**Статус:** одобрен, готов к плану реализации

## Контекст

Приложение «Помощьник Бригадира» — одно, но пользоваться им должны несколько
бригадиров. Сейчас входа нет: кто открыл, тот видит все данные. Нужно: вход
по паролю, у каждого бригадира свой изолированный журнал и (в будущем Этапе 2)
свой список сотрудников. Инвентаризация — общая для всех.

Это Этап 1 — фундамент. Этап 2 (быстрый ручной ввод, список сотрудников)
строится поверх него и оформляется отдельной спецификацией.

## Что общее, что личное

- **Общее для всех бригадиров:** инвентаризация — хозяйства, кварталы,
  клетки, ряды, кусты.
- **Личное у каждого:** журнал записей (`work_logs`), отчёты. (В Этапе 2 —
  список сотрудников.)
- Бригадир видит и меняет строго свои записи.

## Модель данных

### Таблица `brigadiers`
| Поле | Тип | Описание |
|---|---|---|
| id | SERIAL PRIMARY KEY | |
| login | TEXT UNIQUE NOT NULL | логин; уникальность и вход — без учёта регистра |
| password_hash | TEXT NOT NULL | bcrypt-хэш; открытого пароля нигде нет |
| status | TEXT NOT NULL | `pending` / `active` / `disabled` |
| is_admin | BOOLEAN NOT NULL DEFAULT false | |
| label | TEXT | пометка администратора (чей это аккаунт) |
| created_at | TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP | |

### Таблица `work_logs` — добавляется колонка
- `brigadier_id INTEGER` — ссылка на `brigadiers(id)`, изначально nullable.
- Существующие записи при первичной настройке привязываются к админ-аккаунту.

### Таблица `app_settings`
| Поле | Тип |
|---|---|
| key | TEXT PRIMARY KEY |
| value | TEXT |
- Хранит секрет подписи cookie (`session_secret`) — генерируется один раз
  сервером, переживает перезапуски. Задавать вручную не нужно.

## Зависимости (новые npm-пакеты)

`bcryptjs` (хэширование паролей), `jsonwebtoken` (подпись токена входа),
`cookie-parser` (чтение cookie). Все — чистый JS, без нативной сборки,
безопасны для Render.

## Аутентификация

- Пароли хэшируются библиотекой **bcryptjs**.
- Вход хранится в **подписанном JWT-токене в httpOnly cookie**. Токен
  содержит id бригадира, живёт ~1 год (365 дней) — бригадир практически
  никогда не вводит пароль заново. Cookie: `httpOnly`, `secure`,
  `sameSite=lax`. Отключение аккаунта и «Выйти» при этом срабатывают
  мгновенно (статус проверяется на каждом запросе).
- Секрет подписи — `session_secret` из `app_settings` (генерируется при
  первом запуске сервера, если его ещё нет).
- На **каждом** защищённом запросе сервер: читает токен → берёт id →
  загружает бригадира из БД → проверяет `status = 'active'`. Поэтому
  отключение аккаунта администратором действует немедленно.

## Первичная настройка (создание админ-аккаунта)

- `GET /api/setup-needed` → `{ needed: true }`, если в `brigadiers` нет ни
  одной записи с `is_admin = true`.
- Клиент при загрузке вызывает его; если нужно — показывает экран
  «Первичная настройка: создайте аккаунт администратора» (логин + пароль).
- `POST /api/setup` `{ login, password }`: работает **только пока нет ни
  одного админа**. Создаёт аккаунт со `status = 'active'`, `is_admin = true`;
  привязывает к нему существующие записи `work_logs` (где `brigadier_id IS
  NULL`); сразу логинит (ставит cookie). После появления админа `/api/setup`
  возвращает ошибку «Настройка уже выполнена».
- Делается один раз сразу после развёртывания, до раздачи ссылки.

## Регистрация и вход

- Экран входа (для незалогиненных): поля логин + пароль, кнопка «Войти»,
  переключатель на «Зарегистрироваться».
- `POST /api/register` `{ login, password }`: создаёт бригадира со
  `status = 'pending'`. Проверки: логин свободен, пароль не короче 6
  символов. После успеха — экран «Заявка отправлена, ожидайте подтверждения».
- `POST /api/login` `{ login, password }`: проверяет пароль; вход разрешён
  только `status = 'active'`. Сообщения:
  - неверные данные → «Неверный логин или пароль»
  - `pending` → «Заявка ещё не подтверждена администратором»
  - `disabled` → «Аккаунт отключён, обратитесь к администратору»
- `POST /api/logout`: очищает cookie.
- `GET /api/me`: возвращает `{ login, is_admin, status }` вошедшего или 401.
- Кнопка «Выйти» в шапке приложения.

## Админ-страница (только для is_admin)

Отдельный раздел/вкладка, виден только аккаунту администратора.
- `GET /api/admin/brigadiers` — список всех аккаунтов: логин, статус,
  пометка, дата.
- Действия (каждое — отдельный endpoint, требует прав администратора):
  - **«Одобрить»** — `pending → active`
  - **«Отключить»** — `→ disabled`
  - **«Включить»** — `disabled → active`
  - **«Пометка»** — сохранить текст пометки администратора
  - **«Задать новый пароль»** — администратор вводит новый пароль для
    аккаунта (на случай, если бригадир забыл свой); сервер хэширует и
    сохраняет; администратор сообщает новый пароль бригадиру.
- Защита: администратор **не может отключить сам себя** — чтобы не потерять
  доступ.

## Изоляция данных

- В `work_logs` — колонка `brigadier_id`. Все запросы данных привязаны к
  вошедшему бригадиру:
  - `POST /api/process` — новые записи пишутся с `brigadier_id` вошедшего.
  - `GET /api/logs`, `GET /api/report` — только записи вошедшего.
  - `DELETE /api/logs/:id` — удаляет, только если запись принадлежит
    вошедшему.
- Инвентаризация (`/api/estates`, `/api/quarters`, `/api/inventory/...`) —
  требует входа, но **без** фильтра по бригадиру: общая для всех.
- Правило доступа: **все `/api/*` требуют входа**, кроме `/api/register`,
  `/api/login`, `/api/setup`, `/api/setup-needed`. `/health` остаётся
  открытым (нужен для UptimeRobot).
- Новый одобренный бригадир видит пустой журнал.

## Клиент (app.js, index.html)

- При загрузке: `GET /api/setup-needed` → если настройка нужна, показать
  экран первичной настройки. Иначе `GET /api/me` → не вошёл: экран
  входа/регистрации; вошёл: основное приложение.
- Новые экраны: вход, регистрация, первичная настройка, админ-страница.
- Вкладки «Ввод данных / Отчёт / Журнал» и выбор хозяйства показываются
  только после входа.
- Раздел «Админ» виден только администратору.
- Кнопка «Выйти» в шапке.

## Безопасность (репозиторий публичный)

- В коде нет паролей, логинов, секретов.
- Пароли — только bcrypt-хэши, открытого вида нет нигде.
- Админ создаётся через экран первичной настройки — никаких учётных данных
  в коде или переменных окружения.
- Секрет подписи cookie сервер генерирует сам, хранит в БД (`app_settings`).
- Бизнес-данные инвентаризации (названия сортов и т. п.) закрыты входом —
  `/api/quarters` и прочие недоступны без логина.

## Обработка ошибок

- Регистрация: занятый логин → «Логин занят»; короткий пароль → «Пароль не
  короче 6 символов».
- Вход: сообщения перечислены в разделе «Регистрация и вход».
- Не-администратор обращается к админ-endpoint → 403.
- Бригадира отключили во время работы → следующий запрос вернёт 401, клиент
  покажет экран входа.
- `POST /api/setup` после появления админа → ошибка «Настройка уже выполнена».

## Тестирование

- Тест-фреймворка в проекте нет — не добавляем (не ломаем стиль проекта).
- Сервер: `node --check` на синтаксис; ручная проверка endpoint'ов.
- Ключевая ручная проверка изоляции: завести тестового бригадира, одобрить
  его, войти под ним — журнал пустой; войти под админом — видны свои
  записи; убедиться, что бригадир А не видит записи бригадира Б.
- Клиент: ручная проверка на телефоне и в браузере.

## Вне объёма (YAGNI)

- Восстановление пароля по почте (есть админская кнопка сброса).
- Смена бригадиром своего пароля (только админ-сброс).
- Авто-уведомления о новых заявках (администратор сам смотрит страницу).
- Роли тоньше, чем «администратор / бригадир».
- Этап 2 — список сотрудников и карточный ввод (отдельная спецификация).
- Выбор хозяйства остаётся на устройстве (`localStorage`), как сейчас.
